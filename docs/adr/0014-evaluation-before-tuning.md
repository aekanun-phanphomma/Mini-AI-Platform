# ADR-0014: สร้าง evaluation set ก่อนปรับจูน RAG

- **สถานะ:** Accepted
- **วันที่:** 2026-10-19
- **Phase:** 2

## บริบท
การปรับ RAG มีตัวแปรมาก เช่น chunk size, top_k, prompt, model ถ้าตัดสินจากการลองถามแล้วดูเอง
จะไม่รู้ว่าการเปลี่ยนแปลงทำให้ดีขึ้นจริงหรือแค่บังเอิญดีกับคำถามที่ลอง

## การตัดสินใจ
- เขียน `phase-2-llm-rag/eval/questions.jsonl` ที่รู้คำตอบอยู่แล้ว ทั้งคำถามที่ตอบได้และคำถามที่ **ไม่มีคำตอบในเอกสาร** (ต้องตอบ "ไม่ทราบ")
- วัด 2 ชั้นแยกกัน:
  - **retrieval hit rate**: เอกสารที่ถูกต้องอยู่ใน top-k ไหม
  - **answer hit rate**: คำตอบมีคีย์เวิร์ดที่ต้องมีไหม
- script เป็น quality gate: ต่ำกว่าเกณฑ์จะ exit 1
- ใช้ eval set ชุดเดียวกันกับ compose, k8s และ Cloudflare เพื่อเปรียบเทียบ

## ทางเลือกที่พิจารณา
| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| Keyword match (เลือก) | ทำซ้ำได้ (deterministic), ฟรี, เร็ว | หยาบ คำตอบถูกแต่ใช้คำต่างไปจะนับว่าผิด |
| LLM-as-judge | เข้าใจความหมาย | ต้องมีโมเดลใหญ่, ผลไม่คงที่, มี bias |
| RAGAS / DeepEval | มี metric ครบ | dependency หนัก, ต้องใช้ LLM judge |

## ผลที่ตามมา
- ✅ ถ้า retrieval ผิด รู้ได้ว่าต้องแก้ chunking/embedding ถ้า retrieval ถูกแต่คำตอบผิด รู้ว่าต้องแก้ prompt/model
- ⚠️ eval set มีแค่ 9 ข้อ ใช้ตัดสินทางสถิติไม่ได้ งานจริงควรมีหลักร้อยข้อ
- 🔁 แบบฝึกหัด: เพิ่ม LLM-as-judge โดยใช้โมเดลที่ใหญ่กว่า แล้วเทียบผลกับ keyword match
