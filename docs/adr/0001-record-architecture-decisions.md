# ADR-0001: บันทึกการตัดสินใจด้านสถาปัตยกรรมด้วย ADR

- **สถานะ:** Accepted
- **วันที่:** 2026-10-19
- **Phase:** -

## บริบท
แล็บนี้มีเครื่องมือมากกว่า 20 ตัว ผ่านไป 3 เดือนจะจำไม่ได้ว่าทำไมเลือก Qdrant แทน pgvector
หรือทำไม Argo CD ถึงต้องอ่านจาก GitHub
ในทีมจริง คนที่มาใหม่ก็จะถามคำถามเดิมซ้ำ ๆ หรือเปลี่ยนสิ่งที่ตั้งใจออกแบบไว้โดยไม่รู้ผลกระทบ

## การตัดสินใจ
- เก็บ ADR เป็นไฟล์ Markdown ใน `docs/adr/` อยู่ใน repo เดียวกับ code และ review ผ่าน PR เหมือนกัน
- ใช้รูปแบบสั้นตาม [template.md](template.md): บริบท → การตัดสินใจ → ทางเลือก → ผลที่ตามมา
- ADR เขียนแล้วไม่แก้ (immutable) ถ้าเปลี่ยนใจให้เขียน ADR ใหม่ที่ supersede ADR เดิม

## ทางเลือกที่พิจารณา
| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| ADR ใน repo (เลือก) | อยู่ใกล้ code, มี version, review ผ่าน PR ได้ | ต้องมีวินัยในการเขียน |
| Wiki / Notion | แก้ง่าย, ค้นหาง่าย | แยกจาก code, เนื้อหาล้าสมัยโดยไม่มีใครรู้ |
| ไม่บันทึก | เร็ว | ความรู้อยู่แค่ในหัวคน |

## ผลที่ตามมา
- ✅ มีเหตุผลรองรับทุกการเลือก เวลาสัมภาษณ์ตอบได้ว่า "เลือก X เพราะ Y และแลกกับ Z"
- ⚠️ ต้องใช้เวลาเขียนประมาณ 10-15 นาทีต่อการตัดสินใจ
- 🔁 ถ้า ADR ยาวเกิน 1 หน้า แปลว่ากำลังตัดสินใจหลายเรื่องในครั้งเดียว ให้แยกเป็นหลาย ADR
